Try-Catch-Finally の役割 ── 3つの箱で「目的」を完遂する

Concept
Try-Catch-Finally は「目的を諦めない」設計パターン。3つの箱を順番に並べるだけです。
📦
Try（試す箱）
メインの処理 → 成功すれば最高
↓ もし失敗したら…
🚨
Catch（捕まえる箱）
保険処理 → 誰かが気づける
↓ 成功でも失敗でも…
🧹
Finally（必ず走る箱）
最後の処理 → ログ・後片付け
💡 大事なのは順番。 Try → Catch → Finally の3段並びにすると、どんな結果でも目的が達成できるフローになります。

ハンズオン手順 ── 一緒に作りましょう

Hands-on
📝 ステップ概要
  1. 手動トリガー「フローを手動でトリガーします」で開始
  2. Try スコープ を作って、作成（Compose）を入れる
    式に div(1,0) → 必ず失敗する
  3. Catch スコープ を作って、Teams通知を入れる
    実行条件＝失敗・タイムアウト
  4. Finally スコープ を作って、完了ログを入れる
    実行条件＝4つ全部チェック
  5. 失敗テスト：Try ❌ / Catch ✅ / Finally ✅
  6. 成功テスト：div(10,2) に直すと Try ✅ / Catch ⏭️ / Finally ✅
📸 完成形
💪 詰まったら声かけてください。 一緒に進めるので、迷ったときは画面共有でみんなで解決します。

Closing

活用事例とよくあるつまづき

💼 こんな場面で使えます

  • SharePoint 登録失敗時に元データを退避＋担当者に通知
  • 外部 API エラー / タイムアウト時にリトライ用キューへ転送
  • 承認フロー失敗時に上司にエスカレ
  • ファイル取得・変換失敗時に「失敗しました」を即通知

⚠️ うまくいかない時のチェック

  • Catch が動かない → 実行条件の構成で「成功時」のチェックを外したか確認
  • メール送信では失敗しない → 宛先が変でも「受領」で成功扱い。不達は後からメールで返るだけ。だから今日は div(1,0) で確実に失敗させる
  • Catch が常に動く → 「失敗時」「タイムアウト」だけにチェック、それ以外は外す
  • スコープの名前変更でエラー → 半角英数推奨。後続の式は再選択で追従
