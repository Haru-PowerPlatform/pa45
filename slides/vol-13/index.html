テーマ解説 (1/2)：失敗しても気づけない問題

Concept
① 自動化フローの "あるある" な事故

フローを作って業務に組み込むと、ある日突然こんなことが起きます。

📧

宛先のメアドが間違ってた

メール送信が失敗。
でも誰も気づかない。

🔒

SharePoint の権限切れ

登録が失敗。
でもエラー画面はどこ？

🌐

外部APIが一時的にダウン

タイムアウト。
翌日まで気づかない。

② 解決策：失敗を「捕まえる」仕組みを足す

Try-Catch は、失敗しうる処理を「箱」で囲い、失敗したときだけ別の処理を走らせる 設計パターンです。
これでフローは「失敗しても止まらない・誰かが気づける」状態になります。

💡 大切なのは「気づける」こと。　止まらないだけでなく、担当者に通知が飛ぶ仕組みまでがセットです。

PA45｜第13回 ／ アクション 1/3

スコープ ── 処理を「箱」でまとめる

Action
📌 何ができる？

複数のアクションを 1つの箱 にまとめます。
箱単位で「実行条件」を設定できるのが最大のメリット。

どこから追加？
+ 新しいステップ
→ 「コントロール」を選ぶ
→ 「スコープ」をクリック
💼 今日のフローでの使い所

「Try」「Catch」と名付けた2つのスコープを作り、その中にそれぞれメール送信／Teams通知を入れます。

📝 イメージ
📦 スコープ「Try」
✉️ メールの送信 (V2)
📦 スコープ「Catch」
💬 Teams：担当者に通知
※ スコープの「名前」は分かりやすく付け替えるのがコツ
💡 スコープは「役割を分ける箱」。　Try-Catch だけでなく、フローを読みやすくするためにも便利です。

PA45｜第13回 ／ アクション 2/3

実行条件の構成 ── 前のアクションが「どうなったとき」動かす？

Action
📌 何ができる？

アクション（やスコープ）の 「いつ動くか」 を設定します。
普通は「成功したとき」ですが、ここを変えると Catch が作れます。

どこから開く？
スコープ右上の「⋮」(3点メニュー)
→ 「実行条件の構成」
💼 今日のフローでの使い所

Catch スコープに対して 「失敗」「タイムアウト」にチェック → 「成功」のチェックを外す。これだけで Catch ができます。

📸 実際の画面はこれ
☑ 失敗しました
Catchで必須
☑ タイムアウトした
Catchで推奨
☐ 成功しました
Catchでは外す
☐ スキップ済みである
Catchでは外す
💡 ポイント： Catch には「失敗時」と「タイムアウト時」の両方をチェックしておくと、より安心です。

PA45｜第13回 ／ 関数 3/3

メールの送信 (V2) ── 失敗するアクションの代表選手

Action
📌 なぜこのアクション？

「わざと失敗」を再現しやすいアクションだから。
宛先メアドを存在しないものにすれば即エラー。Try-Catch の学習にぴったり。

必須項目
宛先　：送信先メールアドレス
件名　：例「申請を受け付けました」
本文　：申請内容を埋め込む
💼 今日のフローでの使い所

Try スコープの中に置きます。テスト時はわざと 存在しないメアド を入れて失敗させ、Catch が動くのを確認します。

🎭 わざと失敗させる方法
  • 宛先を存在しないアドレスに
    no-such-user@example.invalid
  • 権限のないメールボックスを指定
  • 本文を空のまま送信（環境によっては失敗）
✅ 本番では普通に成功するアクション

講座中はわざと失敗させるだけ。実務では業務メールを送る信頼できる定番アクションです。

🎯 メール送信は Try-Catch 入門の "教材"。 同じ考え方で SharePoint・Teams・外部APIの失敗も捕まえられます。

PA45｜第13回

テーマ解説 (2/2)：Try-Catch の設計思想

Concept
なぜ「スコープで囲う」のか？ それは "ひとかたまり" として失敗を判定する ためです。
❌ スコープなし（残念パターン）
❌ メール送信失敗
→ フローが 止まる
→ 誰も気づかない
→ 翌日「あれ、来てない…」
✅ Try-Catch あり（安心パターン）
❌ Try（メール送信）失敗
→ ✅ Catch が 自動で発動
→ 💬 担当者に Teams 通知
→ その場で対応できる
🧠 覚え方
Try ＝「試す」箱 ── 失敗するかもしれない処理を入れる
Catch ＝「捕まえる」箱 ── 失敗したときだけ動く処理を入れる
Catch の動かす条件を「実行条件の構成」で「失敗時」にするのが鍵
🎯 大事なのは「失敗してもフローが続く」だけじゃなく「気づける」こと。 Catch でちゃんと通知を入れましょう。

PA45｜第13回 ／ ハンズオン 1/3

ハンズオン STEP 1-2 ── Try と Catch を作る

Hands-on
1

スコープ「Try」を作る

  • + 新しいステップ → コントロール → スコープ
  • 名前を スコープ-Try に変更
  • 中に メールの送信 (V2) を追加
💡 ここがメイン処理。失敗するかもしれない処理だけ入れます。
2

スコープ「Catch」を作る

  • もう1つ スコープ を追加 → 名前 スコープ-Catch
  • 中に Teams 投稿（担当者宛）を追加
  • 「⋮」→「実行条件の構成」を開く
  • 失敗・タイムアウト にチェック、成功は外す
💡 これで「Try が失敗したときだけ走る」設定の完成。
✅ ここまでできたら： Try と Catch の間の小さなドットが 橙＋赤 色になっていれば「失敗時のみ」の合図。次は Finally を足します。

PA45｜第13回 ／ ハンズオン 2/3

ハンズオン STEP 3 ── Finally で必ず走る箱を足す

Hands-on
3

スコープ「Finally」を作る

  • 3つ目の スコープ を追加
  • 名前を スコープ-Finally に変更
  • 中に Teams 投稿（完了ログ）を追加
  • 「⋮」→「実行条件の構成」
  • ⭐ 4つ全部 にチェックを入れる
🎯 ポイント：4つ全部チェックする意味

前のスコープが 成功でも・失敗でも・タイムアウトでも・スキップでも 必ず Finally が走る。だから「完了ログ」を確実に残せます。

📸 実際の画面（Finallyの実行条件）
☑ 成功 ☑ タイムアウト ☑ スキップ ☑ 失敗 ── 全部チェック
✅ ここまでできたら： Catch と Finally の間のドットが 4色全部点灯（緑・橙・グレー・赤）。これが「どんな状態でも走る」の合図。

Closing

活用事例とよくあるつまづき

💼 こんな場面で使えます

  • メール送信失敗を担当者に即通知（今日のテーマ）
  • SharePoint 登録失敗時に元データを退避＋通知
  • 外部 API タイムアウト時にリトライ用キューへ転送
  • 承認フロー失敗時に上司にエスカレ

⚠️ うまくいかない時のチェック

  • Catch が動かない → 実行条件の構成で「成功時」のチェックを外したか確認
  • Try が成功しちゃう → わざと失敗させる宛先（example.invalid）になっているか
  • Catch が常に動く → 「失敗時」「タイムアウト」だけにチェック、それ以外は外す
  • スコープの名前変更でエラー → 半角英数推奨。後続の式は再選択で追従
